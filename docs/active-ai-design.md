## Problem Statement

当前 AI 浏览器插件都是「被动 AI」：用户必须主动打开侧栏、输入问题、手动选择要参考的页面。这本质上只是把 ChatGPT 搬进了浏览器，没有消除「用户不知道该问什么」和「AI 不知道用户在干什么」这两个根本问题。

Lumino 要做的「主动 AI」：插件持续观测用户的浏览行为（跨 tab 的页面内容、输入框交互、停留模式），基于多层记忆系统理解用户的短期意图和长期画像，在用户最需要的时刻主动出击——输入框智能补全是第一个场景。

核心理念类比：**普通人在浏览器里的 AI 体验，应该和程序员在 Cursor/IDE 里的 AI 体验一样——多粒度、上下文感知、主动介入。** 输入框补全 = Cursor Tab 自动完成；页面内容定位 = 代码解释；完整任务执行 = AI 实现功能需求。

## What Makes This Cool

- **不是又一个聊天机器人**：AI 自己决定什么时候出现，不需要用户请
- **越用越懂你**：三层记忆 + LLM 管理的用户画像，不是死板的规则匹配
- **基础设施思维**：记忆系统独立于任何场景，输入框补全只是第一个消费者。后续智能 Tab 管理、主动提醒、浏览日报都可以直接复用它

## Demand Evidence

以「程序员 AI 编程工具」为基准类比：
- Cursor/Tabnine/GitHub Copilot 证明「在输入框里主动补全」是用户真实需求，日均触发数百次
- 浏览器的文本输入量远超 IDE 代码输入量——邮件、表单、搜索、文档、聊天，每一个输入框都是一个「光标位置」
- 现有浏览器插件的 copilot 模式仍要求用户「先打开侧栏再提问」，主动式触发当前市场空白

## Target User & Narrowest Wedge

**第一层楔子：输入框智能补全**

在用户聚焦任意网页的 `<input>` 或 `<textarea>` 并开始输入时，AI 基于：
1. 当前 Session 浏览上下文（今天看了哪些页面、搜索了什么、在什么表单里输过什么）
2. 长期记忆中相关的历史浏览行为（语义匹配后加载原始记录）
3. 用户画像（姓名、偏好、近期关注领域）

生成 ghost text 补全建议，以内联 overlay 形式注入页面，不干扰宿主 DOM 结构。

用户按 Tab 接受补全，或继续输入则补全自动消失。

## Constraints

- **Manifest V3 限制**：Service Worker 可能随时被终止，定时任务需用 `chrome.alarms` + 持久状态恢复
- **LLM 上下文窗口有限**：不能把所有历史记录喂给 LLM，必须依赖分层记忆 + 检索
- **跨域限制**：Content Script 可以读页面 DOM，但跨域 iframe 内容不可访问
- **宿主页面兼容性**：注入 overlay 不能破坏任何网站的样式和功能
- **不采集隐私敏感页面**：bank、gov、healthcare 等类别的 URL 自动跳过事件采集

## Premises

1. **记忆系统是基底组件** — agree
   记忆系统（事件采集、日记忆、检索、用户画像）独立于任何消费场景。输入框补全是第一个消费方，未来新增场景只需要调用记忆系统的 `queryContext()` 接口。
   
2. **先用简单字符串匹配，后升级语义检索** — agree
   Layer 3 检索先用 LLM 生成关键词 + 字符串匹配日记忆文件，验证产品价值后再引入 embedding 向量检索。

3. **日记忆写入：定时 batch，非实时增量** — agree
   每日定时（用户配置时间，默认晚上 10 点）调用 LLM 将当天 Layer 1 原始事件总结为一份日记忆。简单可控，避免实时调用的高复杂度和高成本。

4. **用户画像由 LLM 从行为推断** — agree
   不要求用户手动填写个人信息。LLM 从浏览行为中推断并持续更新用户画像。用户也可以手动补充或修正。

5. **第一个场景只做 ghost text 补全，不做弹窗/通知** — agree
   弹窗和通知有打断感，风险高。先从最不侵入的 ghost text 开始验证「主动 AI」的价值。

## Memory System: Layer-by-Layer Design

### Layer 1: 原始浏览事件

**存储表：browsing_events (IndexedDB)**

```typescript
interface BrowsingEvent {
  id: string              // crypto.randomUUID()
  sessionId: string       // 每天一个 session ID（按日期分）
  timestamp: number       // Date.now()
  type: EventType

  // 通用字段
  url?: string
  title?: string
  tabId?: number

  // 按事件类型特有字段
  payload: Record<string, unknown>
}

type EventType =
  | "page_visit"          // 页面加载/激活
  | "page_scroll"         // 滚动深度变化
  | "page_idle"           // 停留检测（同一页面停留超过阈值）
  | "input_focus"         // 聚焦输入框
  | "input_change"        // 输入内容变化（节流）
  | "input_submit"       // 表单提交
  | "text_selection"      // 选中文本
  | "tab_switch"          // 切换标签页
  | "tab_close"           // 关闭标签页
```

**采集策略：**

| 事件 | 采样方式 | 节流 |
|------|---------|------|
| page_visit | Content Script window.onload + SW tabs.onActivated | 无 |
| page_scroll | scroll 事件监听 | 每 5 秒最多 1 次 |
| page_idle | 定时器，30 秒无交互触发 | 每个页面 1 次 |
| input_focus | focusin 事件 | 无 |
| input_change | input 事件 | 每 2 秒最多 1 次，截断至 200 字符 |
| input_submit | 表单 submit 事件 | 无 |
| text_selection | mouseup + getSelection() | 每 3 秒最多 1 次 |
| tab_switch | SW tabs.onActivated | 无 |
| tab_close | SW tabs.onRemoved | 无 |

**隐私过滤（在采集入口处）：**

```typescript
const PRIVACY_DOMAINS = [
  /bank/i, /alipay/i, /paypal/i,
  /gov\\.cn/i, /healthcare/i, /hospital/i,
  /accounts\\.google\\.com/i, /login/i
]
```

### Layer 2: 日记忆

**存储表：daily_memories (IndexedDB)**

```typescript
interface DailyMemory {
  date: string            // "2026-05-10"
  summary: string         // LLM 生成的摘要
  topics: string[]        // ["日本旅行", "React文档", "购物比价"]
  keyUrls: string[]       // 当天最重要的 URL
  eventCount: number      // 当天事件总数
  createdAt: number
  updatedAt: number
}
```

**写入策略：定时 batch**

1. chrome.alarms 每日定时触发
2. 读取当天所有 browsing_events → 发送给 LLM → 写入 daily_memories
3. SW 被终止时，下次启动检查空缺日期并补写

### Layer 3: 检索

**流程：**

```
输入框聚焦
  ↓
1. 收集当前 Session 上下文（当前 url/title/页面摘要 + 输入框上下文 + 最近 10 个 page_visit）
  ↓
2. LLM 生成检索关键词（3-5 个）
  ↓
3. 字符串匹配 daily_memories 的 summary + topics 字段
  ↓
4. 命中 → 加载 keyUrls 对应的原始 browsing_events 合并到上下文
   未命中 → 只用当前 Session 上下文 + 用户画像
  ↓
5. 汇总 → 生成补全建议
```

## Scene 1: 输入框智能补全

### 触发条件

1. 聚焦 input[type=text|search|email|url] 或 textarea 或 contenteditable
2. 不在隐私过滤域名下
3. 输入 >= 2 字符 + 停止 500ms
4. 每个输入框最多 5 次补全请求

### UI: Ghost Text Overlay

- 半透明灰色文字，绝对定位在输入框内部
- Tab 接受 / Escape 关闭 / 继续输入不匹配则消失

### LLM 调用

- System prompt 注入用户画像 + 当前浏览上下文 + 相关历史记忆 + 输入框描述
- User message 只包含用户已输入的内容，LLM 返回补全部分

## The Assignment

本周做一件事：**手工在浏览器里跟踪自己一天的浏览行为**——每打开一个页面、每次切换 tab、每次在输入框里打字，用笔记下来。晚上看这些记录，问自己：「如果 AI 看到了这些，在什么时刻主动介入会让我觉得『哇，这个有用』？」这样你会在写代码之前就知道 Layer 1 到底该采集什么信号。

### 结构调整说明

1. **db.ts** — 设计文档中未列出，但实际需要。原计划 `thread-idb.ts` 和记忆系统各自管理 IndexedDB 连接，会导致版本号冲突。统一为 `src/lib/db.ts` 提供唯一连接，所有模块共享，数据库名 `lumino`，含三张表：`threads`、`layer1_events`、`daily_memories`。

2. **memory-idb.ts** — 设计文档未列出。原计划 `event-store.ts` 和 `daily-memory.ts` 直接操作 `chrome.storage.local`，实际改为存 IndexedDB（容量更大、支持索引查询）。`event-store.ts` 变为 thin wrapper，委托 `memory-idb.ts`。

3. **ghost-overlay.ts** — 设计文档中计划独立文件，实际合并到 `input-watcher.ts` 中。ghost overlay 与输入监听紧密耦合，拆分会增加消息复杂度，合并更简洁。

4. **Side Panel 架构** — 聊天 Tab 和主动 AI Tab 用 `display: none/flex` 切换，而非条件渲染（`{tab && <Component/>}`）。后者会销毁/重建 DOM，导致聊天状态丢失。

### 存储架构

| 数据 | 存储位置 | 容量 | 清理策略 |
|------|---------|------|---------|
| 聊天会话（threads） | IndexedDB `lumino` / `threads` | 无上限 | 手动删除 |
| Layer1 事件 | IndexedDB `lumino` / `layer1_events` | 5000 条 | 7 天过期 + 超量删旧 |
| 日记忆 | IndexedDB `lumino` / `daily_memories` | 90 天 | 超 90 天自动删除 |
| 用户画像 | `chrome.storage.local` | ~1KB | 每 6h 更新，不删除 |
| Session 时间戳 | `chrome.storage.local` | 8 bytes | 24h 后重置 |
| LLM 配置 | `chrome.storage.sync` | ~200 bytes | 手动修改 |

### 补全触发流程

```
用户输入 ≥2 字符 → 停止 500ms
  → Content Script (input-watcher.ts) 发消息到 Background
  → Background (completion-engine.ts):
      1. buildCompletionContext() 汇聚画像 + Session上下文 + 检索记忆
      2. 构建 system prompt + user message
      3. requestChatCompletionTurn() 调用 LLM
      4. 结果发回 Content Script
  → Content Script 渲染 ghost overlay
  → 用户按 Tab 接受 / Escape 关闭 / 继续输入自动消失
```

### 已知限制

1. **首次使用无记忆** — 新用户没有日记忆和画像，补全仅依赖当前页面的 placeholder 和用户已输入文本
2. **LLM 未配置时** — 补全不可用（静默跳过），日记忆生成基础统计摘要（无 LLM）
3. **Content Script 注入** — `lumino-input-watcher.ts` 在 `<all_urls>` 下运行，有性能开销。隐私域名已通过 `privacy-filter.ts` 跳过采集，但 DOM 事件监听仍会注册
4. **bfcache 警告** — 开发模式下 Chrome 会报 `message channel is closed`，不影响功能，可通过 `chrome://flags/#back-forward-cache` 关闭
